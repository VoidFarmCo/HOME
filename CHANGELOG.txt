Pueo - changelog
================

Firmware for a handheld multi-radio field tool on the ESP32-2432S028R.
Forked from CiferTech's ESP32-DIV at 90f7967, 2026-09-01.

Nothing here has run on hardware. Every release below compiles clean and
several fixes are verified at the symbol level, but no version has been
flashed to a board. Treat inherited feature claims as inherited.

Digests for each release are in dist/pueo-<version>.sha256.


0.2.8 - 2026-09-19
------------------

Address rotation fails loudly instead of silently.

  * bleRotateAddressNow() restarted advertising when the address change
    failed, but never checked whether the restart itself succeeded. If a
    board dislikes the stop/set/start the symptom would have been a spoofer
    that mysteriously stops transmitting, once a second, with nothing said
    on screen and nothing in the log.

  * Each step is now checked and named: "stop refused", "set addr refused",
    "restart refused". Three consecutive failures latch rotation off and put
    one line on screen saying which step it was.

  * Advertising is restarted whatever happened in between. Silently going
    dark is worse than a stale address, and a stale address is what every
    release before 0.2.7 did anyway.

  * Entering a spoofer resets the latch, so a transient refusal does not
    disable rotation for the rest of the session.

+760 bytes.

0.2.7 - 2026-09-19
------------------

The BLE spoofers stop transmitting from one fixed address.

Bluetooth:

  * BLE Spoofer, Sour Apple and AirTag Spoofer now rotate their BLE address
    once a second. All three built a random address and then dropped it on
    the floor - nothing called esp_ble_gap_set_rand_addr, setOwnAddrType or
    ble_hs_id_set_rnd - so every packet went out from the ESP32's one fixed
    address. A stream of a dozen different Apple products sharing an address
    is not a disguise, and it made the transmitting device attributable for
    as long as it ran.

    This was documented rather than fixed in 0.2.4, because making the
    spoofers harder to attribute is an increase in what they do rather than
    a correction to what they claim. That is the owner's call and it has now
    been made.

  * Non-resolvable private, not static random. ble_hs_id_gen_rnd(1, ...)
    asks the stack for an NRPA, which is the address type the specification
    defines for exactly this; a static random address is meant to hold still
    for a power cycle, so rotating one is out of spec even though the
    controller allows it. Letting the stack generate it also sidesteps the
    top-two-bits rule, which the old dead code got right once (0xC0) and
    wrong twice - 0xF0, and on the wrong end of the array for NimBLE, which
    takes the address little-endian.

  * Once a second rather than once a burst, because the controller refuses
    HCI_LE_Set_Random_Address while advertising is enabled, so a rotation is
    stop, set, start. AirTagSpoofer carries a note that repeated stop/start
    was resetting the board, so rotating every 40 ms burst is the exact
    pattern to avoid. kBleAddrRotateMs is the dial if the board turns out to
    tolerate more. On a failure advertising restarts on the old address
    rather than staying dark.

  * AirTag Spoofer's address display reads the stack instead of a kept copy.
    NimBLEDevice::getAddress() prefers the PUBLIC address and only falls back
    to random when there is no public one, which on an ESP32 never happens,
    so it would have gone back to confidently showing the one address the
    radio is not transmitting from. ble_hs_id_copy_addr(BLE_ADDR_RANDOM, ...)
    gets the real one.

+504 bytes. The four NimBLE symbols are in the linked image, checked with nm
rather than assumed - including ble_hs_hci_util_set_random_addr, which is
what actually issues the HCI command.

0.2.6 - 2026-09-19
------------------

A crash fix, the enclosure carrying the logo, and a way to see the screens
without a board.

Fixed:

  * Opening the second Bluetooth page would have faulted the device. Adding
    Fast Pair in 0.2.5 raised BT_PAGE1_FEATURES from 2 to 3 but left
    bluetooth_page1_icons with two initialisers, so the third was null and
    displayPagedSubmenu() handed it straight to drawBitmap. It compiled
    clean: an array with fewer initialisers than its size is legal C++ and
    neither -Wall nor -Wextra warns.
  * tools/check_menu_tables.py now walks every label and icon table in the
    sketch and asserts each has as many initialisers as its declared bound,
    and that a menu's labels and icons share a size constant. 28 tables, 12
    pairs. Run against the bug first to confirm it fails on it.

UI:

  * A selected menu tile is FILLED with the accent, with its icon and label
    dropped to the background colour. It used to move a 1 px border and the
    label from white to accent - and the icon did not change at all, since
    every icon table is already UI_ICON and SELECTED_ICON_COLOR was defined
    as UI_ICON again. On a 100x60 tile that was the whole cue. Both grids,
    the main menu and "More". Flash is byte-identical: a constant swap.
  * SELECTED_ICON_COLOR is deleted, having no users left. It would not have
    tripped -Wunused; it was a #define.
  * "by: magikh0e" on the boot screen, under the artwork. The logo height
    ceiling in Branding.h moved with it: four lines under the logo is a
    62 px block and caps the logo at 217 px, where three lines and 46 px
    capped it at 249. At the shipped 200 px there are now 8 px of slack
    rather than 24.

Enclosure:

  * The owl is debossed into the chin of the lid, 30 mm at 0.6 mm deep.
    LOGO = false turns it off and produces an STL identical to the pre-logo
    one, triangle for triangle.
  * Debossed rather than embossed because the artwork is line art: the
    thinnest 5% of strokes are 8 px of a 474 px height, so at 30 mm they
    land at 0.51 mm - one extrusion wide on a 0.4 nozzle. A raised rib that
    thin shears off; the same feature cut in is a channel that cannot.
  * tools/trace_logo.py turns the PNG into outlines with marching squares
    and Douglas-Peucker, since OpenSCAD cannot usefully extrude a bitmap
    and there is no potrace here. It rasterises what it wrote and refuses
    to write when more than 3% disagrees with the source; at the shipped
    tolerance it is 0.02%.
  * docs/pueo/logo-fit-test.scad is a 76 x 56 x 3 tile to print first. The
    lid is a tray, so it must print face-down or its ceiling is an 80 x 165
    bridge - which puts the logo against the bed. The tile carries the same
    owl on both faces to show which side does it better, plus a ladder of
    eight grooves 0.3 to 1.6 mm wide at the shipped depth.
  * tools/check_logo_scale.py asserts the artwork's height, width, centring
    and area at three sizes, and the lid's removed volume. It exists
    because the first version rendered the owl at 7.9 mm instead of 30 and
    11 mm off centre, and two renders were inspected without noticing.
    OpenSCAD converts SVG px to mm at a fixed 96 dpi; resize() measures the
    box that turned up instead of assuming one.

Documented:

  * docs/pueo/jammers.md, to the same standard as the Fast Pair probe. The
    two radios are not the same story. BLE Jammer and Proto Kill set
    RF_CONT_WAVE with the power bits at maximum, so they are an unmodulated
    carrier - certain. SubGHz Jammer sets 2-FSK at +12 dBm and calls
    SetTx(), and nothing is ever fed to it: no FIFO payload, and TX_PIN is
    only ever driven LOW. What radiates is NOT established, and no
    constant-wave bit is set, so nothing in the code states the intent.
  * Also recorded there: none of the three can report whether they worked,
    and none ever will, because knowing you had suppressed a link means
    receiving it.

Tooling:

  * tools/render_screens.py draws the boot screen, main menu and Bluetooth
    submenu to PNG from the firmware's own bitmaps and TFT_eSPI's own font
    data, at the coordinates the source gives. Not a mockup - the text is
    the panel's 5x7 GLCD font and its 16 px proportional font. Version and
    byline come from Branding.h so the images cannot go stale.
  * art/ is out of the source archive: 7389 KB -> 6166 KB. It was a 1.3 MB
    photograph whose only job is regenerating a bitmap already committed in
    icon.h. The merged image's digest does not move, because the firmware
    never depended on it.

0.2.5 - 2026-09-19
------------------

Google's side of the BLE world, which this device had never looked at, plus
a Flipper .sub reader and two more advertisement templates.

Bluetooth:

  * New feature: Fast Pair, on page 1 of the Bluetooth menu. Two halves that
    are deliberately not the same act.

    Listening is passive - a BLE scan with active scanning off, reading the
    0xFE2C service data every Fast Pair device broadcasts unasked.

    Probing transmits. It opens a GATT connection to ONE device the operator
    selected and writes 80 bytes to the key-based pairing characteristic, to
    test for CVE-2025-36911. It sits behind a confirm screen that names the
    target address and states what will be sent, it never runs on its own,
    and it never touches more than the selected row. Point it at your own
    devices or ones you have permission to test.

  * ESP32-DIV/FastPair.{h,cpp} parses the advertisement. Fast Pair lives in
    BLE service data, not manufacturer data, which is why the three
    Apple-shaped parsers already here were structurally incapable of seeing
    one.

    A payload is a 24-bit Model ID only when it is exactly three bytes. Every
    other length is a not-discoverable frame - flags, account key filter,
    optional salt and battery - with no Model ID anywhere in it. Reading its
    first three bytes as one produces a confident, plausible, meaningless
    number, and since most earbuds already belong to somebody that is the
    common case rather than the edge case.

  * Nothing correlates devices across address rotation, because Fast Pair
    deliberately offers nothing to correlate on. A Model ID names a model,
    not a unit, so two strangers with the same earbuds share one. An account
    key filter is a salted bloom filter whose salt rotates precisely so a
    passive listener cannot follow the device. Two tests assert those
    non-properties, so adding correlation later means deleting a test that
    says why not.

  * The model-name table is empty on purpose. Google's mapping needs an API
    key, and the lists circulating for "fast pair spam" tools are IDs chosen
    to provoke a popup, with names that are often wrong. An unknown ID prints
    as six hex digits, which is true.

  * BLE Spoofer gains Microsoft Swift Pair and Flipper Zero, device types 22
    and 23. Both built from primary sources.

    Swift Pair sends sub scenario 0x00, pairing over LE only. The other two
    values the spec defines describe a dual-mode peripheral and 0x01 also
    requires a BR/EDR address in the same advertisement; this has none, so
    sending either would advertise a capability that is not there. Several
    spam tools send 0x03, which the spec's table does not define at all. The
    display name is Pueo-XXXX rather than a real product's, so the operator
    can tell their own notification from a stranger's.

    Flipper uses service UUID 0x3080 with the hardware colour in the low
    bits - from Flipper's own serial profile, not from captures - so
    0x3081-0x3083 are one service on differently coloured hardware.

  * Found, not changed: devices_uuid is handed to addServiceUUID()
    immediately before setAdvertisementData(), which replaces the whole
    payload, so it never reaches the air. It also carries 9000 where the
    Bluetooth base UUID has 8000. Removing it should change nothing, but
    that is analysis rather than a measurement.

Sub-GHz:

  * ESP32-DIV/SubFile.{h,cpp} reads Flipper .sub captures. Pueo's own export
    is a binary blob with a magic number that nothing else can read; .sub is
    what the rest of the sub-GHz world trades in.

    RAW files are refused by name, three ways - Filetype, Protocol: RAW, and
    RAW_Data. They share the key file's header and carry microsecond timings
    where the key would be, and a SubGhzProfile has nowhere to put timings,
    so half-parsing one yields a profile that looks valid and transmits
    nonsense.

    Only Princeton claims an rc-switch protocol number, because Princeton is
    PT2262/EV1527 and rc-switch protocol 1 is the same thing. CAME, NICE
    FLO, Holtek and the rest parse and return protocol 0 with the name kept.
    Their timings do not match an rc-switch number and a guess would
    transmit something subtly wrong while presenting as correct.

  * Nothing calls the .sub reader yet. Wiring it in is a UI change -
    saveProfile() reads globals rather than taking a profile, and there are
    only five EEPROM slots, so an import has to ask which to replace.

Checked:

  * tools/check_fastpair.py, 80,111 checks. Every fuzz input asserts
    (frame == ModelId) == (len == 3), which is the whole rule in one line.
  * tools/check_fastpair_probe.py, 50,293 checks, most of them on the
    provider address at bytes 2..7. That field is the test: a probe broken
    so subtly that every device reports "no response" is indistinguishable
    from a room full of correctly-behaving devices.
  * tools/check_sub_parse.py, 60,891 checks, including every single-byte
    mutation of a valid file.
  * tools/check_ble_adv.py, 1,095 checks. Walks each advertisement the way a
    receiver does and insists the walk lands exactly on the packet's end - a
    wrong AD length byte still transmits, still looks right in the log, and
    is silently dropped by everything that hears it. It also walks the three
    older fixed templates, which had never been checked; all are well
    formed. The Google one decodes as a discoverable Fast Pair frame
    advertising model ID 00B727, one fixed model, never varied.

Fixed while writing the above:

  * mbedtls here is 2.28, so the 3.x MBEDTLS_PRIVATE field accessor was
    wrong.
  * deriveKey() called mbedtls_ecp_point_init instead of _free in its
    cleanup, leaking a point per probe.

Still true: none of this has run on hardware. The Fast Pair probe's crypto
path in particular has never derived a key against a real provider. Treat
the first run on real hardware as the first test of it.

0.2.4 - 2026-09-19
------------------

Mostly reading what features already claimed, and fixing what turned out
not to be true.

WiFi:

  * The promiscuous filter is global and sticky, and nothing set it back.
    Two features asked for management frames only, so Packet Monitor - which
    wants data frames, because it writes them to its pcap and counts them on
    screen - saw management frames only if the captive portal or Karma had
    run first in the same session. No error, no empty file, just a capture
    missing everything that was not a beacon. Every feature that reads
    frames now states what it wants each time it starts.
  * Packet Monitor recognises WPA handshakes in the frames it was already
    recording. ESP32-DIV/Eapol.{h,cpp} finds the 802.1X payload by computing
    the header length from the frame control field rather than testing a
    fixed offset, so it still works on a frame carrying a fourth address or
    an HT Control field; the four messages are told apart by three bits of
    the Key Information field, plus the Key Type bit so a group rekey is not
    mistaken for M3. The header shows how many networks have M2 and M3.
  * Forcing a handshake by deauthenticating a client is deliberately NOT
    wired up. The decision logic exists, disarms on capture and after six
    bursts, and nothing calls it - Packet Monitor runs in WIFI_MODE_NULL and
    cannot transmit anyway. See docs/pueo/eapol-capture.md.

Bluetooth:

  * AirTag Sniffer can tell a separated tag from somebody's phone. Apple
    uses type 0x12 for both the long form that carries the rotating public
    key, which a device broadcasts once separated from its owner, and a
    short online status ping that every participating iPhone and Mac emits.
    They differ in the length byte, which the parser had and never read.
    Battery and the maintained flag are decoded from the status byte, which
    was being stored and never shown. Scanning is passive now: an AirTag
    advertises non-connectable, so the scan requests bought nothing.
  * BLE Scanner drew manufacturer and service data as text, with
    String((char*)raw.c_str()), which stops at the first zero byte. Apple's
    company identifier is 4C 00, so every Apple device displayed as the
    single letter L. Both are hex now, capped to the row width. Tx Power is
    guarded by haveTXPower() like the fields below it, rather than printing
    whatever was left in the field.
  * Skimmer Detect's signatures carry a Radio column. It scans BLE only, so
    eleven of its twenty-eight names can never match, including seven of the
    eight rated 5 - HC-05 and HC-06 among them. Kept and marked rather than
    removed. The table's order is load-bearing and now says so.
  * Sniffer's two alerts are annotated rather than changed. Jamming
    Suspected fires on any device seen more than twenty times, a counter
    that is never reset, so about two seconds of a normal beacon. MAC
    Spoofing Suspected cannot detect a MAC change at all: the row is found
    by matching that exact address. See docs/pueo/ble-sniffer.md.

Sub-GHz:

  * One frequency list instead of two identical copies in different
    namespaces, which nothing kept in step.

Tooling:

  * tools/check_eapol.py and tools/check_airtag_parse.py, modelling the
    parsers against synthetic frames behind a buffer that refuses any read
    outside them.


0.2.3 - 2026-09-19
------------------

Tooling and documentation only. The compiled image is identical to 0.2.2
apart from the version string.

  * CHANGELOG.txt, this file, now ships inside the archive and sits beside
    the downloads, so deciding whether to flash an image does not mean
    unzipping the source first.
  * tools/make_release.sh takes PUEO_PUBLISH_DIR: a directory to copy the
    finished artifacts and the changelog into, verified with sha256sum -c
    afterwards. An environment variable rather than a path in the file,
    because the file ships inside the archive.
  * The same script now refuses to re-cut a version already in dist/ unless
    --force is given. Re-running it on a released version silently produced
    a different archive - the script is itself inside the archive - while
    the digest published beside it stayed as it was.
  * How to verify an archive, and where, is written down in that script:
    extract to a short path and delete it afterwards. A deep path fails on
    Windows' 259-character limit, and a junction from a short path to a deep
    one defeats -ffile-prefix-map and quietly breaks reproducibility.


0.2.2 - 2026-09-19
------------------

Licensing:

  * Relicensed to GPL-3.0-or-later. Upstream's MIT notice is kept verbatim
    in LICENSE.MIT and those portions remain available under MIT.
  * RF24 removed. It is GPL-2.0-only and could not lawfully share a binary
    with arduinoFFT (GPL-3.0-or-later) or NimBLE-Arduino (Apache-2.0) - a
    conflict inherited from upstream's dependency set and carried since
    0.1.0. It was the only GPLv2-only library in the tree, so the merged
    image is distributable again.
  * ESP32-DIV/Nrf24Raw.{h,cpp} replaces it: the nRF24L01+ register
    interface, scoped to power, channel and an unmodulated carrier.
    MouseJack, the ESB paths and the skimmer detector never used RF24 -
    they already drove the registers directly - so only the jammers had to
    change. 3,476 bytes smaller.
  * docs/pueo/licensing.md records the dependency table, the grants it is
    read from, and why "version 2" and "version 2 or later" was the whole
    question.

Spotter:

  * Fingerprints the probe-request information-element set, so a camera
    that randomises its MAC can still be followed. FNV-1a over the elements
    a device emits; ids always, contents only where they belong to the
    device rather than to that probe, which leaves the SSID and the channel
    out deliberately.
  * One device is one row when it changes address. A new address folds into
    an existing row on a fingerprint match, but only when both addresses
    are locally administered: two cameras of one model share an element
    set, and merging on the fingerprint alone would report one where there
    are two.
  * Rows show whether the address is made up, how many times it has
    changed, and how long the device has been in range.
  * Capture to SD on the Log button, off until switched on. One row per
    device, and every device rather than only the matched ones.
  * No fingerprint signature table ships. The values need captures off real
    hardware. See docs/pueo/ie-fingerprinting.md.

Fixes:

  * The jammers hop on purpose now. They configured three RF24 objects over
    three channel groups, which reads as twelve channels across three
    radios and was neither: the board profile maps all three chip selects
    onto one module, and the setup loop called startConstCarrier once per
    channel with each call replacing the last. The hopping that did work
    was in the feature loops, picking a random channel every iteration and
    writing it three times. Now round-robin on a 4 ms dwell, written once.
  * onPacket no longer discards wildcard probe requests. A zero-length SSID
    ended processing of the frame, which threw away the full element set
    those frames carry.

Tooling:

  * tools/fuzz_ie_walk.py, tools/check_spotter_merge.py and
    tools/check_spotter_capture.py model the parts that cannot be tried on
    hardware that does not exist: 65,543 frames through the element walk
    with no out-of-bounds read, sixteen merge rules, sixteen capture rules.


0.2.1 - 2026-09-19
------------------

  * SpotterSignatures.h: Axon body cameras under a new Bodycam kind
    (00:25:DF is Axon Enterprise's own IEEE block, so Strong), and the
    union of the flock-you and flock-finder community OUI collections - 33
    prefixes, plus the Flock SSID variants, the Penguin battery pack's BLE
    name and XUNTONG company ID, and the Raven GATT UUIDs.
  * Every prefix was resolved against the IEEE MA-L registry first, which
    is why nearly all land on Weak: 23 belong to Liteon and 2 to Espressif,
    blocks that appear in a great deal of unrelated consumer hardware. Each
    carries the assignee the registry names rather than the word "Flock".
  * The build stopped writing the build machine's home directory into the
    firmware. NimBLE's assert macros bake __FILE__ in, so the absolute path
    of every asserting source file was in the published 0.1.0 and 0.2.0
    images - seventeen strings of it. -ffile-prefix-map rewrites them.
    Side effect: the merged image no longer depends on where it was built,
    so a rebuild at any path matches the published digest.
  * docs/pueo/nrf24-fit-test.scad: a test print for the one enclosure
    pocket with no nominal slack.

0.1.0 - 2026-09-18
------------------

First release of the fork.

  * board_pueo.h: a board profile resolving the pin conflicts in the stock
    CYD map, as an overlay rather than a fourth board branch.
  * SpiBus.{h,cpp}: one owner for the SPI bus the display, SD card and all
    three radios share, and the fix for touch losing it to the radios. The
    resource that conflicts is the GPIO matrix rather than the clock - MISO
    is an input and exactly one GPIO can drive it.
  * Spotter: passive detection of ALPR cameras and smart glasses. Receive
    only; it never transmits, associates or deauthenticates.
  * gps.cpp: gpsPortOpen/gpsPortClose bracket every UART open and close and
    hand GPIO 1 between the console and the GPS.
  * wifi.cpp: removed an out-of-bounds write in both deauth frame builders.
  * A brightness step that wrapped: stepping up from 248-254 dropped the
    backlight to almost off.
  * -w and -zmuldefs removed from the build, and the underlying issues
    fixed rather than silenced. The one load-bearing duplicate symbol is
    handled by weakening the SDK symbol instead.
  * IR support dropped: 140 KB that could never run on a board with no IR
    hardware.
  * tools/check_pinmap.py resolves the pin macros the way the compiler will
    and fails the build on a collision.
